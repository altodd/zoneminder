# zmng code review (correctness, robustness, security)

Scope: `zmng/src/*.rs` (api, config, db, detect, import, main, mp4, recorder, retention, thumbs, video) and `zmng/web/app.js`, reviewed against `docs/ARCHITECTURE.md` §3–§4 and the retina 0.4.20 source. Build: `cargo build` clean (6 dead-code warnings), `cargo test` 7/7 pass, clippy not installed on this toolchain. Verified on the live instance (127.0.0.1:8080, setup mode) and the real Front Door HEVC segments under `scratchpad/zmng-test/storage1/1/20260927/`.

Severity: **P0** loses recordings / corrupts files · **P1** security · **P2** playback correctness · **P3** robustness · **P4** performance · **P5** style. Line numbers are from the files as they were at review time (the tree was being edited during the review; `recorder.rs` unchanged since 17:33, others 17:52–17:57).

## Verified correct (no action)

* **mp4.rs box layouts** against ISO 14496-12: `ftyp` (`iso5`, minor 512, compat `iso5 iso6 mp41 dash`), `mvhd` v0 (108 B), `tkhd` v0 flags 7 (92 B), `mdhd` v0 (32 B, `und`), `hdlr` (`vide`, name NUL-terminated), `vmhd` flags 1, `dinf/dref/url ` flags 1, `stsd` entry_count 1, empty `stts/stsc/stsz/stco` (stsz has sample_size + count), `mvex/trex` with default description index 1. Fragment: `mfhd` 16 B, `tfhd` flags `0x020000` (default-base-is-moof, 16 B), `tfdt` v1 (20 B), `trun` flags `0x000F01` = data-offset|duration|size|flags, `data_offset = moof_len + 8` (points at the first mdat payload byte; asserted by the roundtrip test and by ffprobe reading every packet), sample flags `0x02000000` (depends_on=2, sync) for keyframes and `0x01010000` (depends_on=1, non-sync) otherwise. `debug_assert_eq!(w.buf.len(), moof_len)` guards the arithmetic.
* **Index blob**: 32 B/entry LE (`i64 dts, u32 dur, u64 off, u32 len, u32 samples, u8 motion, 3 pad`), round-trips; `chunks_exact` ignores a trailing partial entry.
* **Truncation tolerance**: `scan_segment`/`scan_segment_file` drop a trailing partial box and an orphan `moof` without `mdat`; adopted `bytes` = end of the last complete fragment, so `segment_file`'s `total` never exposes the garbage tail. `scan_segment_file` handles `size==0` (to EOF) and `size==1` (largesize) and caps `moof` at 16 MB. `adopt_file` does *not* read whole files any more (only headers + moofs); a 1 GB orphan is fine.
* **RFC 6381**: HEVC `general_profile_compatibility_flags` is read big-endian (flag[0] = MSB in the stream) and `reverse_bits()` puts flag[31] at the MSB as 14496-15 Annex E requires (0x60000000 → `6`); constraint bytes are trailing-zero trimmed in original order; level = `payload[12]`; tier H/L; profile space A/B/C. Cross-check: our derivation on the imported Hikvision files gives `hvc1.1.6.L150.80`, identical to retina's `rfc6381_codec()` for the same camera model. `avc1.PPCCLL` correct.
* **Timestamps on the real files** (`ffprobe -show_packets` on `215655.mp4`, 1080 packets, and on the served `range.mp4`, 1098 packets): dts strictly increasing, dts == pts, `duration == next dts − dts` for every packet, durations ∈ {2970, 3060, 5940, 6030} ticks (the camera's 30 fps RTP clock decimated to 18 fps; 5001 ticks average), first packet of every fragment `K_`, 60 keyframes per 60 s file. **The ffmpeg warning "non monotonically increasing dts … 1496 >= 1496" is not our bug**: it appears only when *decoding* to `-f null` (reproduced), never with `-c copy -f null` (silent). The null muxer rescales to a 1/30 s timebase (from `r_frame_rate=30/1`), and a 2970-tick (0.99 frame) interval rounds to the same index as its neighbour.
* **Recorder anchoring math**: `elapsed_90k = elapsed * 90000 / clock_rate` in `i128` (no overflow for any clock rate); `dts_from_wall` in `i128`; retina's `enforce_timestamps_with_max_jump_secs(10)` rejects backward RTP jumps, so `dts <= last_dts` can only come from re-anchoring (F9). Duration lookahead is right: the last sample of GOP *n* gets its duration from GOP *n+1*'s keyframe *before* `flush_gop`, and across a segment close the keyframe correctly becomes the first sample of the next file (verified: 0 inter-fragment gaps in the index, segments are 60.02 s / 1080 frames). `must_close` at the first keyframe ≥ 60 s matches the design.
* **Live ring/broadcast**: `Recent` keeps init + 3 fragments; new viewers get init + last fragment (one GOP latency); init resend on change is compared by bytes.
* **db.rs**: every `format!` in `events()` only interpolates `i64`s, an operator literal and `?N` placeholders; all values are bound. `update_camera` interpolates only column names from `ALLOWED`. `update_event_progress` uses pre-update `score` semantics correctly (`MAX(score,?1)`, `CASE WHEN ?1>=score`). `close_stale_events` (`COALESCE(peak,start)+5 s`) is sane. `busy_timeout=5000`, WAL, `synchronous=NORMAL` (a power loss may lose the last row but the file is adopted by reindex — good design). Indexes cover `segments_in_range` (cam,end / cam,start), `segments_older_than` (cam,end), `oldest_segments` (storage,start), `events_in_range` (cam,start).
* **api.rs ACL**: every media/metadata route resolves the camera id first and calls `can_see` (`segments/{id}/file.mp4|init.mp4|frag/…` via `seg.camera_id`; `events/{id}*` via `e.camera_id`; `events?camera=` intersected with the visible set; `stats` filtered). ## Details and scenarios

### F1 — open segment lost on session exit
`run_camera` runs `tokio::select! { r = record_session(..) => r, _ = stop.changed() => return }`. `record_session` owns `seg: Option<OpenSegment>`, `gop` and `pending`; on `?` errors ("no packets for 20 s", "stream error", `open_segment` I/O errors, `insert_segment` errors) or when the future is dropped by the `stop` arm, all three are dropped. `OpenSegment` has no `Drop`, so the file is closed by the OS with everything written so far, but no row exists. Scenario: camera reboots at 12:00:30 → the 12:00:00 file (30 s) is on disk, absent from the index; the timeline shows a hole from 12:00:00 to the reconnect; an event at 12:00:20 never gets a thumbnail; retention's byte budget under-counts by that file. Repeat for 23 cameras and every network blip. Fix sketch:

```rust
loop {
    let item = tokio::select! {
        i = tokio::time::timeout(Duration::from_secs(20), demuxed.next()) => i,
        _ = stop.changed() => break,
    };
    … // on Err: `result = Err(e); break;`
}
if let Some(p) = pending.take() { gop.push(Sample { dts: p.dts, duration: last_delta, .. }); }
flush_gop(&mut gop, &mut seg, h);
close_segment(ctx, cam, storage, sample_entry_id, seg.take())?;   // always
result
```
plus `retention::adopt_camera_dir(db, storage, cam.id)` at the top of `record_session`.

### F2 — write errors corrupt the index
`flush_gop` builds `entry.offset = s.pos` and does `s.pos += frag.len()` regardless of `write_all`'s result. With ENOSPC after 30 fragments, entries 31..60 point at bytes that do not exist; `close_segment` inserts the row with `bytes = s.pos` (larger than the file). `segment_file` then answers `Content-Length` for bytes it cannot read; `stream_plan`'s `read_exact` fails; `frame_at`/thumbnails 500. If the write is *partial* (EIO on a network FS), every later real fragment lands at a smaller offset than recorded and the index points into the middle of NAL data.

### F3 — old segment inserted with the new sample entry
Order in the parameter-change branch: intern new entry → `sample_entry_id = new` → flush pending (fake 3000) → `flush_gop` → `close_segment(.., sample_entry_id /*new*/, ..)`. The file's own `moov` is the old one (HLS fine); `plan_range` emits `init_segment(new)` before those fragments.

### F9 — re-anchor and the +1 bump
The bump exists to keep `tfdt`/durations strictly increasing, which is correct, but it is only ever exercised after a backwards re-anchor, and then it produces exactly the pathology it was meant to avoid (1-tick durations) for a burst of frames. Preferable: `dts = dts.max(last_dts + min_frame_dur)` where `min_frame_dur` is e.g. the smaller of the last observed delta and 90000/60, and never let a re-anchor move `dts` below `last_dts` (slew by at most a few ms per frame instead). Segment names: `OpenOptions::create_new(true)`; on `AlreadyExists` append `-1`, `-2`.

### F12 — camera patch validation
`detect_width = 0`: `frame = vec![0; 0]`; `read_exact(&mut [])` is `Ok(())` without reading, so the loop spins, `feed` returns 0 every iteration, `MotionLog::push` runs at MHz rate (ring bounded at 4096, but lock contention with the recorder's `max_in`), and when ffmpeg exits nothing notices because EOF is only observed on a non-empty read.

### F15 — event cap
`EventState` has no `start_dts`; the cap compares against `peak_dts`, which is updated on every new maximum. The live test camera (`lavfi testsrc`) shows it: event 4 opened at 22:04:47 with score 185, peak moved to 210 at 22:06:32, so it ends no earlier than 22:16:32 unless a higher score arrives first.

### F19 — parser bounds and default durations
`parse_moof` reads `traf[p+12..p+20]` for a `tfdt` of declared size ≥ 8 without checking `s >= 20`, and walks `trun` entries with `q` unbounded by `p+s`. A file truncated inside a `moof` header is caught by the outer size check, but a file with a plausible outer size and a corrupt inner size panics; `reindex` runs at startup in `main.rs:199` before anything else, so one bad file prevents the daemon from starting. Separately, ffmpeg (ZoneMinder passthrough) sets `tfhd.default_sample_duration` and omits per-sample durations when they are constant; our parser then reports `duration 0` (seen on the final fragment of both imported events).

### F20 — HLS
Playlist header (verified live): `#EXTM3U / VERSION:7 / PLAYLIST-TYPE:VOD / INDEPENDENT-SEGMENTS / TARGETDURATION:2 / MEDIA-SEQUENCE:0`, then per file `EXT-X-MAP:URI="/api/segments/N/file.mp4",BYTERANGE="758@0"` and per fragment `PROGRAM-DATE-TIME / EXTINF:1.001, / BYTERANGE:len@off / URI`. Only the DISCONTINUITY-without-MAP case is off spec.

### Timestamp sanity (the 18 fps question)
Histogram of sample durations in `215655.mp4`: 495×6030, 236×2970, 225×5940, 124×3060 ticks (sum 5 401 710 = 60.02 s, 1080 samples → 5001.6 ticks ≈ 17.99 fps). The camera's encoder runs a 30 fps RTP clock and skips every third frame-ish; the alternation 6030/2970 (not 6000/3000) is the camera's own ±30-tick jitter, faithfully recorded. No duplicates, no zeros, no 1-tick samples, and the served range concatenation (`range.mp4`, two files) is also strictly monotonic.

## Suggested order of work
1. F1 + F2 (recorder exit paths and write errors) — these are the only findings that lose recordings.
2. F4 + F5 + F21 (setup-mode exposure, division-by-zero, login hardening) before the port is reachable from the LAN.
3. F3, F9, F15, F16, F8 (correctness of what gets played back / listed).
4. F10, F11, F12, F13, F19 (robustness at 23 cameras / on spinning disks / against bad input).
5. F6, F7, F14 before the index grows to weeks of data.
